System

Travel Secretary

旅行の曖昧な希望から候補比較・日程確認・予約準備まで進め、購入直前だけ承認を求める。

Skill: Travel Secretary

Input examples

  • 来月どっか旅行したい
  • 温泉行きたい
  • 3日くらい暇だからどこか
  • このイベントに合わせて宿と移動を取って

Pipeline

1. Intent — 日程、目的、予算、人数、必須条件を既知Contextから埋める

2. Calendar — 接続済み予定との衝突を確認

3. Discover — 目的地/イベント/季節条件を調査

4. Route — 鉄道/航空/その他の現実的な移動候補を作る

5. Stay — 宿候補を比較

6. Preference — private Contextの座席・交通・宿の好みを適用

7. Cost — 交通+宿+現地固定費の概算

8. Critic — 営業日、乗継、チェックイン、キャンセル条件、総額、根拠を確認

9. Recommend — 原則1案を第一候補、必要なら代替1–2案

10. Booking capability — 予約経路ごとに「検索できる」「空室確認できる」「入力できる」「確定できる」を実測する

11. Approval — 購入/予約確定の直前だけ本人へ確認

12. Book — 許可されたToolで実行

13. Verify — 予約番号、日時、金額、取消条件を再確認

14. Calendar — 確定後に予定反映

15. Record — 旅程の必要情報だけruntime stateへ

Booking routing

予約サイト名を固定しない。現在利用できる能力を確認し、次の順で人間作業が最小になる経路を選ぶ。

1. 正規の予約Tool / connector / provider APIで安全に予約まで完結できる経路

2. 予約事業者自身のAI/agentで予約まで完結できる経路

3. 公式サイトまたは予約サイトをCloud Browser等のブラウザエージェントで操作する経路

4. 検索・空室取得API + ブラウザ予約の組合せ

5. どれも使えない場合だけ、予約条件を埋めた最短の手動導線を本人へ渡す

Capability check

宣伝文や過去情報だけで「予約できる」と判断しない。実際の現在の機能を確認する。

  • SEARCH: 条件に合う施設/便を探せるか
  • AVAILABILITY: 指定日・人数の在庫を確認できるか
  • FILL: 宿泊者情報等を入力できるか
  • COMMIT: 予約確定まで実行できるか
  • VERIFY: 確定結果を別の証拠（確認画面・メール等）で検証できるか

途中で能力不足が判明したら本人へ戻さず、次の経路へ自動フォールバックする。

例: 予約サイトAIが日付指定できない → 通常予約画面 + browser agent。

Approval boundary

検索、比較、空室確認、予約フォームの準備は原則自動で進める。

料金発生、予約確定、取消料が発生する変更、新しい個人情報の外部送信は本人承認後。

承認時は施設/便、日時、人数、総額、重要な取消条件を短く提示する。

Failure handling

  • Toolが無いことと、予約不能を混同しない。
  • 一つの予約経路が失敗しても旅行計画全体を止めない。
  • 画面仕様変更に依存する細かいクリック手順をSkillの中核にしない。
  • モデルや外部サービスが改善したら、より少ない手順で完遂できる経路を優先する。
  • 「予約したはず」で終了せずVerifyを必須にする。

Human effort target

本人が検索結果20件を比較しない。

本人に返すのは原則:

「この案が一番合う。総額約X円。これで予約する？」

予約経路が失敗した場合も、可能な限り本人にサービス選択や再検索をさせず自動で次へ進む。
